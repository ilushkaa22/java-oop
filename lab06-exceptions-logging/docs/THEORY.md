# Исключения и логирование — понятное объяснение

## 1. Зачем нужны исключения

Обычно метод получает аргументы, выполняет работу и возвращает результат. Но иногда результата нет: книга не найдена, файл отсутствует, год записан словом.

Исключение — объект, который сообщает о такой ситуации и прерывает обычный ход выполнения. В нём есть тип, сообщение и stack trace — цепочка вызовов, по которой видно, где возникла проблема. Также может быть `cause` — исходная причина.

```java
Book book = repository.findById(999);
System.out.println(book.getTitle());
```

Если первая строка выбросила исключение, вторая не выполняется. Java ищет подходящий `catch`: сначала в текущем методе, затем у вызывающего метода и дальше по цепочке. Если обработчик так и не найден, поток завершается с необработанным исключением. В нашей программе это был бы основной поток `main`.

```text
Main вызывает findById(999)
             ↓
Repository не находит книгу
             ↓
throw new BookNotFoundException(...)
             ↓
Обычное выполнение findById прервано
             ↓
catch в Main получает объект исключения
             ↓
finally выполняет завершающее действие
             ↓
Программа продолжает работу после try/catch/finally
```

## 2. Иерархия и два вида исключений

```text
Throwable
├── Error                          unchecked
│   └── OutOfMemoryError
└── Exception
    ├── IOException                checked
    ├── BookNotFoundException       checked
    └── RuntimeException           unchecked
        ├── NumberFormatException
        └── InvalidBookDataException
```

Checked — проверяемое исключение. Компилятор требует, чтобы вызывающий код либо перехватил его через `catch`, либо объявил передачу выше через `throws`. Так устроен `BookNotFoundException` в этой работе.

Unchecked — непроверяемое исключение: компилятор не требует ни `catch`, ни `throws`. Это `RuntimeException`, `Error` и их подклассы. `InvalidBookDataException` наследуется от `RuntimeException`.

**Оба вида возникают во время выполнения программы.** Слово checked означает проверку обработки компилятором, а не возникновение ошибки при компиляции.

| Ситуация в работе | Тип | Почему так в задании |
| --- | --- | --- |
| Книга не найдена | `BookNotFoundException` | Вызывающий код обязан явно решить, как реагировать |
| Пустое название или неверный год | `InvalidBookDataException` | Переданы данные, нарушающие правила объекта |
| Не удалось прочитать файл | `IOException` | Операция зависит от внешней среды |

Отсутствие книги можно было бы выразить и через `Optional<Book>`, но методичка требует собственное checked-исключение. `Error` обычно не перехватывают: это серьёзные проблемы выполнения, например нехватка памяти, и обычная обработка бизнес-ошибок к ним не подходит.

## 3. Throw и throws

```java
public Book findById(long id) throws BookNotFoundException {
    // ...
    throw new BookNotFoundException("Книга не найдена");
}
```

- `throw` — действие: выбросить конкретный объект исключения прямо сейчас.
- `throws` — объявление в сигнатуре метода: такое исключение может выйти из метода наружу.

`throws` не ловит исключение и не создаёт его. Это часть контракта метода.

Собственное исключение — обычный класс. `extends Exception` делает его checked, а `extends RuntimeException` — unchecked. Вызов `super(message)` передаёт сообщение родительскому классу; затем его можно получить через `getMessage()`.

## 4. Try, catch и finally

```java
try {
    Book book = repository.findById(999);
    System.out.println(book); // Не выполнится, если книга не найдена.
} catch (BookNotFoundException e) {
    System.out.println(e.getMessage());
} finally {
    System.out.println("Попытка поиска завершена");
}
```

`try` содержит операцию, которая может завершиться исключением. `catch` описывает реакцию на подходящий тип исключения. `finally` выполняет завершающее действие при обычном выходе из конструкции, в том числе после `return` или при исключении.

Утверждение «finally выполняется абсолютно всегда» неточно: например, при `System.exit()` или принудительном завершении процесса выполнение блока не гарантируется. Не стоит писать `return` или бросать новое исключение в `finally`: они могут скрыть исходный результат или ошибку.

Несколько `catch` располагают от конкретного типа к общему: сначала `NoSuchFileException`, затем `IOException`. Обратный порядок не скомпилируется, поскольку первый обработчик уже перехватывает все случаи второго.

Перехват сам по себе ничего не исправляет. В этой программе реакция определена явно: неправильную строку пропускаем, при ошибке файла заканчиваем текущую загрузку, но продолжаем демонстрацию. Ранее загруженные книги остаются в хранилище.

## 5. Зачем нужен try-with-resources

Ресурс — объект, который после использования нужно закрыть: например, reader для чтения файла. Закрытие освобождает связанный файловый дескриптор; у writer также завершается запись буферизованных данных.

```java
try (BufferedReader reader = Files.newBufferedReader(path, StandardCharsets.UTF_8)) {
    String line = reader.readLine();
} catch (IOException e) {
    LOGGER.error("Не удалось прочитать файл: {}", path, e);
}
```

Try-with-resources автоматически вызывает `close()` у ресурса, реализующего `AutoCloseable`. Закрытие происходит и после успешной работы, и при исключении. Несколько ресурсов закрываются в обратном порядке их объявления.

Если ошибка возникла и в теле `try`, и при закрытии, исходная ошибка сохраняется, а ошибка закрытия добавляется как suppressed exception — сопутствующее исключение. Его можно получить через `getSuppressed()`. Это отличается от `cause`: причина объясняет происхождение основной ошибки, а suppressed-исключение возникло дополнительно.

Для файлов используем try-with-resources; `finally` оставляем для других завершающих действий — например, вывода итогов загрузки.

## 6. Почему проверка должна быть до присваивания

```java
public void setTitle(String title) {
    if (title == null || title.isBlank()) {
        throw new InvalidBookDataException("Пустое название");
    }
    this.title = title;
}
```

Проверка выполняется до изменения поля, поэтому неудачная попытка не портит существующий объект. Если сначала присвоить значение, а затем выбросить исключение, объект останется с неправильными данными.

Конструктор вызывает сеттеры, чтобы правила были одинаковыми при создании и изменении. Если конструктор выбрасывает исключение, выражение `new Book(...)` не возвращает вызывающему коду готовый объект.

Условие `title == null || title.isBlank()` использует короткое замыкание: когда первая часть истинна, вторая уже не вычисляется. Поэтому у `null` не вызывается `isBlank()`.

## 7. Цепочка причин

```java
try {
    int year = Integer.parseInt("не число");
} catch (NumberFormatException e) {
    throw new InvalidBookDataException("Год должен быть целым числом", e);
}
```

Внешнее исключение объясняет проблему в терминах задачи, а `cause` сохраняет техническую причину. Если передать только `e.getMessage()`, связь с исходным объектом и его местом возникновения потеряется. В полном логе причина показана после `Caused by:`.

## 8. Логирование: что произошло и где искать причину

Лог — журнал событий приложения. Исключение меняет ход выполнения программы; запись в лог сохраняет сведения о событии. Вызов `LOGGER.error(...)` сам по себе не бросает исключение и не останавливает метод.

SLF4J — API, то есть интерфейс, через который код отправляет сообщения. Logback — реализация, которая форматирует их и направляет в консоль или файлы. Appender — компонент, отвечающий за конкретное место вывода.

```text
Book / Repository / Main
          ↓ вызовы Logger из SLF4J
       Logback
          ├── CONSOLE → консоль
          ├── FILE → logs/application.log
          └── ERROR_FILE → logs/errors.log
```

| Уровень | Назначение в работе |
| --- | --- |
| TRACE | Самые подробные шаги; в этом проекте не требуется |
| DEBUG | Количество объектов при `findAll()` |
| INFO | Успешное сохранение, удаление, итоги загрузки |
| WARN | Поиск или удаление отсутствующей книги |
| ERROR | Некорректные данные и ошибки файлов |

Порог `INFO` пропускает `INFO`, `WARN`, `ERROR`, но скрывает `DEBUG` и `TRACE`. Для просмотра DEBUG запусти `java -Dlog.level=DEBUG -jar target/lab06-exceptions-logging-1.0.0.jar`.

```java
LOGGER.info("Объект сохранён: id={}", id);
LOGGER.error("Ошибка чтения файла: {}", path, e);
```

`{}` — место для подстановки аргумента. Во втором вызове последний аргумент `e` передаёт исключение целиком, включая stack trace. Параметризованные сообщения позволяют не собирать строку заранее, если уровень отключён; сами выражения аргументов при этом всё равно вычисляются.

В этой лабораторной ERROR при валидации требуется методичкой. В реальном приложении уровень для обычной ошибки пользовательского ввода выбирают по контексту. Не всякое исключение означает критический сбой всей программы.

## 9. Что делает pom.xml

`pom.xml` — описание Maven-проекта: версия Java, зависимости и плагины сборки. В №5 нужна была библиотека JUnit для тестов. В №6 добавлены `slf4j-api` и `logback-classic` для работы программы.

`maven.compiler.release=17` задаёт целевую версию Java и доступный стандартный API. Папки `src/` и `test/` указаны явно, поскольку структура проекта отличается от стандартной Maven. Конфигурация `logback.xml` лежит в `src/main/resources/` и попадает в classpath — набор мест, где Java ищет классы и ресурсы.

Shade-плагин собирает приложение и библиотеки в один JAR. Поэтому достаточно `java -jar ...`: отдельно указывать пути к библиотекам не нужно.

## 10. В каком порядке читать код

1. `exceptions/BookNotFoundException.java` и `exceptions/InvalidBookDataException.java`: различие родителей и передача сообщения/причины.
2. `Book.setYear()`: проверка, ERROR, `throw`, присваивание только корректного значения.
3. `Repository.findById()`: поиск, WARN, checked-исключение и `throws`.
4. `Main.demonstrateRepository()`: обработка в `catch` и действие в `finally`.
5. `Main.parseBook()` и `loadBooks()`: цепочка причин, вложенная обработка строк и автоматическое закрытие файла.
6. `logback.xml`: направления вывода и порог уровней.
